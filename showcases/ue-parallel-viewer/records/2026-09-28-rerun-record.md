## Two different recovery failure classes

The run exposed two materially different failure modes.

### G9-class external execution wedge

```text
Worker generates a bad execution shape
→ shared external execution resource is occupied
→ semantic state may be durable
→ but normal continuation/recovery capacity is impaired
```

### G32-class physical conversation failure

```text
exact browser conversation reaches response-start
→ page remains busy for hours
→ no rendered assistant message
→ no durable Reply/Result
→ semantic completion never arrives
```

G32 is important because it shows that response-start is not enough to prove that a physical conversation will eventually produce usable semantic output.

## What was learned about recovery

Part 2 does not establish that recovery is solved.

It shows which mechanisms began to help:

- backup Runner capacity preserved progress during a blocked primary path;
- semantic-sync recovery could finalize an already-durable result;
- retention/binding hotfixes restored continuation;
- Helper could be evolved from diagnosis toward active recovery and return-control.

It also shows what remained weak:

- externally destructive Worker-authored execution could still monopolize shared infrastructure;
- the physical ChatGPT page could remain in a long-lived busy/non-responsive state;
- the then-current system lacked a complete automatic path for retiring and retrying that physical page without confusing physical retry with semantic generation.

## Current engineering direction

This case is directly driving active work on:

- physical Worker/Planner conversation watchdogs;
- same-generation physical retry;
- deterministic dead-conversation stop/delete/original-wake reinjection;
- stronger separation between semantic failure and physical/transport failure;
- a semantic Helper role that owns bounded recovery mutations, durable closure and return-control;
- redundant execution capacity for externally blocked jobs.

These mechanisms are still being debugged and validated.

## Final interpretation

Part 1 already provides strong positive evidence that CAH can run a long, multi-workstream task to real acceptance when failures remain within the normal task/replanning envelope.

Part 2 identifies the next reliability boundary:

> **The missing capability is not ordinary replanning. It is recovery after strong external interference — when Worker-authored execution blocks shared infrastructure or the browser conversation itself stops responding.**

That is the engineering problem the system is now being strengthened to address.
