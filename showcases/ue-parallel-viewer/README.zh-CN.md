# 并行测试：Blender 资产转 UE／Cook ＋ Viewer 编写

[English](README.md) · [AI 操作说明](AGENT_VIEWER.md) · [证据与时间线](evidence.json) · [下载](DOWNLOADS.md)

**一个任务，两项互相配合的产出：**把已有的 Blender 相机转换为 Unreal 可加载的 Cook 资产，同时完成用于检查它的原生 Viewer。两条工作线最终汇合，以“真实包能打开、材质能看清、工具能用”为验收目标。本案例记录 2026 年 9 月 20 日的 CAH 协同执行，以及随后根据用户反馈完成的交互修正。

## 任务与起点

目标不是再造一个完整编辑器，而是打通一个实用流程：Blender 产出资产，转入 UE 配置材质并 Cook，再通过轻量查看入口检查真正的 UE 显示结果。人可以旋转观察；AI 可以在静默模式下通过接口选择视角、检查信息、获取截图。

相机来自[前一轮 Blender 案例](../camera/README.md)，Viewer 和资产准备脚本也已有暂停的初版。因此，这轮是**复用成果后的全新调度与验收测试**，不是宣称两套软件都在短暂并行时间内从零写完。验收要求包括真实模型与材质、清晰画面、材质槽和依赖信息、可用交互、输入包哈希不变，以及实际可启动的交付入口。

## 如何分工，为什么值得并行

| 角色 | 负责内容 | 交付给下一环节 |
|---|---|---|
| 前台 Foreground | 确认需求、中继本地执行、看图验收和用户交付 | 已确认任务与最终结果 |
| Task Cell | 当前环境判断、拆分、依据真实结果重新规划 | 影响后续执行的具体决定 |
| 执行线程 A | Viewer 源码准备、启动入口、联调脚本与修复 | 能接收真实资产包的查看器 |
| 执行线程 B | 已有 Blender 相机导出、UE 导入和材质配置、预览、Cook | 实际包文件和资产清单 |

两条准备线输出不同，具备独立推进价值；最终联调必须使用资产线真正返回的清单，不能预先假设一个文件名就当完成。环境还未验证时只做一次本机检查，不为了双线程而拆分。

**本地只有一个 runner，原生工具任务按顺序执行。**两个 Worker 同时工作，不等于两套 UE 同时编译。相机修复规划期间，前台还利用空闲 runner 完成独立的 Viewer 原生验证，之后保留结果而不是重跑。

## Task Cell 如何实际影响执行

**先验证现状，不相信过时的阻塞记录。**旧结果写着缺编译环境，但机器已经修复。新的原生检查进入了真正的 C++ 编译，暴露出小范围源码问题。Task Cell 选择针对性修复和复测，而不是要求用户重新安装工具链。

**失败在哪个阶段，就续跑哪个阶段。**相机导入最初错误地直接访问灯光组件属性；决定改成组件查询，同时复用已生成的 FBX。修复后，模型和材质成功导入，但“请求截图后立即退出”导致进程虽返回零，却没有生成图片。Task Cell 因此改为等待真实截图完成，再继续 Cook，不重做已经成功的导出和导入。

**合流不只看接口返回。**Viewer 的 Editor-hosted `-game` 模式需要实际可用的 Pak 平台层、挂载／资产目录处理和运行时着色器库。早期 API 检查通过后，截图仍偏黑，日志还显示缺失着色器，不能据此宣布材质正确。后续限定在 Viewer 显示路径内修复，直到原始材质着色器加载并得到清晰原生画面。

这些决定在相关执行之前形成，确实改变了后续工作。前台仍承担请求中继、部分修复和看图验收，所以案例证明的是有实际作用的任务级协调，而不是完全无人监督的自动派发。

## Worker 换手后有没有丢进度

测试在阶段边界**人为注入一次模拟停滞**，让线程 A 经过已有换手机制更换 Worker，Task Cell 保持不变。接班者读取检查点，识别 Viewer 准备和原生基线已完成，接着准备剩余联调，没有重建既有成果。

这不是实际观察到上下文压缩，也不代表所有额度、模型和生命周期异常都经过测试。它验证的是本案例的一次受控换手及进度复用。

## 从能出图到真正好用

用户反馈推动了交付后的修正。浅色地面曾改善可见性，却挡住从下往上的观察，最终改成无地板的全域浅色环境。操作提示按最终要求使用正常大小的英文绿色文字。

![没有地板遮挡的原生仰视](images/below.png)

鼠标改为按住拖动时捕获、松开即释放。Windows 输入事件测试读取了系统捕获状态，验证按下、拖动、松开、移出窗口、Esc 释放和 Ctrl+Q 正常退出。静默模式在接口就绪时没有可见 Viewer 窗口，仍能调用 API 并生成原生截图。另提供无控制台 VBS 入口；已有启动检查实际调用的是 PowerShell，不能把它说成逐帧检测过所有 VBS 启动闪窗。

过程也并非全程顺利：输出文件声明遗漏曾遮蔽原始故障，共享分支并发更新曾打断结果回写，启动脚本修改也出现过换行转义错误。私库保留失败记录，公开案例保留这些教训，不伪装成一次完美执行。

## 成果与复用

验收的相机包含 **9 个材质槽、7 项依赖**。首轮完整联调生成正面／透视与 Lit／Unlit／Wireframe 组合的六张图，之后追加底面和仰视检查。**150,124,353 字节的 PAK** 在查看和显示／交互修正前后保持同一 SHA-256。结构信息、看图结果与只读校验是相互补充的证据。

本地交付包括人用入口、AI 静默入口、`/v1` 接口和[独立的 AI 操作说明](AGENT_VIEWER.md)。当前使用已安装的 **UE 5.6.1 Editor，以 `-game / DX11 / SM5` 运行**，不是脱离 UE 的独立程序。已验证经典 PAK 相机样例，不宣称通吃任意游戏和 IoStore 资源。

[下载页](DOWNLOADS.md)说明 Viewer 包的状态和依赖。**不附带 UE 本体。**CAH 原许可证保持不变；直接链接 UE 的 Viewer 模块需要单独确认分发许可，公开下载暂待该项决定。
